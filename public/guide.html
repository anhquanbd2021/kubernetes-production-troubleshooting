Incident guide

Four failures, one habit

Every incident in the lab is graded the same way production triage works: read the evidence before you name the cause, name the cause before you touch anything. This page maps each incident to the sequence it drills.

Fixture cluster. Pods, nodes, events, and alarms are canned fixtures chosen to be realistic — nothing here is a live cluster.

The four incidents

What each one teaches

INC-1 · scheduling

Pod stuck Pending

A Pending pod means the scheduler looked at every node and found none that fit. The container never started — there are no logs to read.

First command
kubectl describe pod — the Events block carries the scheduler's refusal: Insufficient cpu, taints, or an unbound claim.
Drills
Reading events before assuming runtime trouble; telling "a state" (get pods) from "a reason" (describe).
Fix
Adjust requests — or add tolerations / bind the volume, whichever the events name.
INC-2 · runtime

CrashLoopBackOff

The pod schedules, the container starts, exits, and the kubelet restarts it with backoff. Now you have logs — the window is just short.

First commands
kubectl logs and kubectl logs --previous for the container that actually crashed, paired with describe pod for the exit code.
Drills
Separating app bugs from config bugs from limits from probes — Exit Code: 1 is not OOMKilled, and a probe that never ran cannot be the killer.
Fix
Whatever the evidence names — here, a ConfigMap key the Deployment references but nobody created.
INC-3 · control plane

etcd storage full

Existing pods run fine, but kubectl apply fails and new Deployments stall. The cluster is alive but frozen — etcd hit its quota and refuses writes.

First commands
kubectl get --raw=/healthz/etcd, then etcdctl endpoint status and etcdctl alarm list — the NOSPACE alarm is the smoking gun.
Drills
The recovery order: defrag → compact → disarm. Disarming before freeing space just re-alarms — the lab refuses it, like the real runbook should.
Fix
Defragment, compact old revisions, then disarm — and automate maintenance so it does not recur.
INC-4 · routing

404 through the Ingress

Pods are Running, the cluster is healthy, users get 404 Not Found. The request arrived — it was just routed wrong, so you walk the chain it traveled.

First command
kubectl get ingress, then hop by hop: Ingress rules → Service targetPort → Endpoints → Pod labels → app routes.
Drills
An empty Endpoints list means no pod matches the selector — the 404 lives at exactly one hop of the chain.
Fix
Align the selector with the pod labels (or relabel the pods) — then endpoints populate and the 404 disappears.

Architecture

Run locally

Inspect the evidence

npm test        # engine grading paths + server routes
npm run prove   # all four incidents driven correctly, PASS lines printed
npm run check   # both
npm start       # serve the lab on :3000

The engine is a plain ES module — the same file the browser imports is the file the tests exercise.

Limits

What this demo does not claim

  • Commands are canned — you cannot type arbitrary kubectl. The outputs are realistic fixtures, not a live API server.
  • The etcd sequence teaches the real order (defrag → compact → disarm); it does not simulate quota tuning, revisions, or multi-member raft detail.
  • Grading checks order of operations — read evidence, diagnose, then fix — not deep knowledge. A guessed diagnosis that happens to be right still fails if no evidence was read first.
  • One happy-path root cause per incident. Real Pending pods and CrashLoops have more branches; the article's decision trees cover them.
